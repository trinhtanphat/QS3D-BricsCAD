# QS3D Level/Floor generated ownership contract

Updated: 2026-08-10 (UTC+7)

## Purpose

QS3D currently models building Levels through `FloorDefinition`. A Floor is **not a `ProjectElement`**, so future native Level heads/elevation symbols must not be generated by pretending that an unrelated semantic element owns them.

`FloorGeneratedIdentityPlanner` provides a CAD-independent identity/freshness contract for future generated Level output without changing project schema or adding a duplicate Level store.

## Stable owner identity

The canonical Floor ID follows `ProjectFloorService` limits:

- trim whitespace;
- 1..64 characters;
- invariant-uppercase canonicalization because Floor lookup is case-insensitive.

The full owner key is length-prefixed and Core derives a compact SHA-256 token:

`LVO1:<64 lowercase hex chars>`

The **owner token stays stable** when the Floor name or elevation changes. This is intentional: a Level symbol representing the same semantic Floor must remain the same replacement owner even after the Floor moves vertically or its display name is edited.

## Separate state identity

Generated Level text/geometry must still become stale when displayed state changes. Core therefore creates a second state key from:

1. canonical Floor owner key;
2. exact trimmed Floor display name (1..120 characters, matching `ProjectFloorService`);
3. finite `ElevationM` formatted with invariant round-trip `R` precision.

Its compact fingerprint is:

`LVS1:<64 lowercase hex chars>`

The **state token changes** when name or elevation changes while the `LVO1` owner remains unchanged. Future native replacement/health can therefore distinguish stable ownership from stale displayed geometry.

## Why elevation is not part of owner identity

If elevation were part of the owner token, moving a Floor from +3.600 m to +3.650 m would create a new owner and make the old native symbol look foreign. Separating `LVO1` from `LVS1` allows a local builder to find the same owned output, verify ownership, and replace its stale state atomically.

## No duplicate semantic Level model

This contract deliberately:

- reuses `FloorDefinition`;
- does not add `ElementCategory.Level`;
- does not add another Levels collection;
- does not use `ProjectElement` generated-handle slots;
- does not change `.qsdb` schema in this slice.

Vertical element references remain the existing `FloorId`, `BottomLevelId`, `TopLevelId` and offset semantics owned by `ProjectFloorService`.

## Future native Level symbol tuple

A local V25 implementation should persist/verify at least:

1. project identity;
2. canonical Floor ID;
3. `LVO1` owner token;
4. `LVS1` state token used to build the symbol;
5. generated CAD handle(s);
6. generated ownership version and symbol/style fingerprint.

Replacement should find output by stable Floor owner identity, verify all live native ownership before erase, then replace geometry/text and update the state token inside one reviewed cross-layer operation. Health should distinguish missing output, foreign ownership and stale `LVS1` state.

Deleting a Floor must not silently transfer its generated symbol to another Floor. A future delete integration needs an explicit generated-output cleanup/refusal contract just as semantic element deletion already respects references.

## Runtime boundary

Core identity + smoke + static preflight are `REMOTE_DONE`. Native Level head/elevation symbol creation, annotation plane/layout, XData encoding, Undo/Redo and real DWG behavior remain `LOCAL_ONLY` until adapter source and exact-SHA BricsCAD V25 evidence exist.

A future local matrix should cover:

- same Floor ID with changed name/elevation retains `LVO1` but changes `LVS1`;
- negative/zero/positive elevations;
- Unicode Floor names;
- symbol replacement after elevation edit without leaked old output;
- foreign/corrupt ownership refusal;
- Floor deletion/reassignment lifecycle;
- save/reopen, Undo/Redo and multi-DWG isolation.

Do not implement native Level symbols by assigning ownership to an arbitrary model element. `FloorGeneratedIdentityPlanner` exists so Floor-owned generated output can have its own stable lifecycle.
